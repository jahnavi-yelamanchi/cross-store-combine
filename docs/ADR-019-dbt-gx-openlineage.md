# ADR-019: dbt diff layer with Great Expectations and OpenLineage

- Context: the policy engine resolves conflicts record by record in Python; there was no warehouse view of all stores side by side, no declarative data tests on the resolved entities, and no record of which datasets a run read and wrote.
- Decision: a dbt-core + dbt-duckdb project in `dbt/` reads the frozen JSONL in place (dbt-duckdb `external_location` with `read_json_objects`), maps each store to canonical names/units in `stg_<store>__<entity>` models generated from `stores/mappings` by `scripts/gen_dbt_staging.py` (which also writes policy source priority into dbt vars), and builds `reconciled_*` (per-store values, `n_sources`, `conflict_fields`, policy pick) and `canonical_*`. GX 1.x validates `canonical_customers` with a JSON suite in an ephemeral context; `xstore.quality.run_all` wraps dbt build + checkpoint in OpenLineage START/COMPLETE/FAIL events (file transport locally, HTTP when `OPENLINEAGE_URL` is set). Snowflake and BigQuery are profile targets only.
- Alternative rejected: a Python loader into raw DuckDB tables before dbt (CI runs bare `dbt build`, so loading must live inside dbt); dbt packages such as dbt_utils/dbt_expectations (need `dbt deps` and network); a GX file context (writes stores and docs sites on every run).
- Why: generated staging keeps SQL in sync with the YAML mappings and `--check` catches drift; reading JSON as objects makes schema drift a NULL instead of a binder error and lets `json_type` flag type drift against each store's majority type; full build is about 4 s offline.
- Consequence: conflicts are exact-value disagreements on non-null values (no fuzzy or tolerance match, recency ignored); the planted orphans make the orders relationship test warn (error only above 100); `runs/.gitkeep` is committed so DuckDB can create the warehouse; run_all closes dbt-duckdb's cached handle (an adapter internal) before GX reads the file.

# ADR-021: Data contracts as domain-owned data products, drift opens an issue

- Context: each store's native schema was implied by `stores/mappings/*.yaml`; a renamed or retyped field upstream surfaced only as a failed `to_canonical` or a silent coercion deep in the pipeline, with no owner to tell.
- Decision: one `contracts/<store>.yaml` per store (data mesh: owner team, domain, version, policy) declaring native fields, types, required, primary key, enums, units, PII, freshness SLA and quality rules; bootstrapped once by `scripts/gen_contracts.py` from mappings plus the canonical Pydantic models, then hand-owned. `xstore.contracts.check` checks records from a live `Store`, a frozen snapshot or a clean synthetic company; schema drift (incl. a rename heuristic), missing required fields and enum breaks fail, type drift warns below the contract's threshold. Failing `store.entity` pairs become one deduplicated GitHub issue (REST via httpx) only with `XSTORE_OPEN_ISSUES=1` and a token, else a dry-run JSON in `runs/contract_issues/`.
- Alternative rejected: coercing drifted records in the mapping layer (hides producer breakage and moves the fix to the wrong team); Great Expectations suites as the contract (no owner/version/PII metadata and not readable by producers).
- Why: the producing domain owns the schema and gets a ticket with sample keys; CI gates contract or mapping edits on a clean sample, while the nightly run on frozen v1 exercises the drift path end to end.
- Consequence: frozen v1 always fails the check (its injected renames are found 62/62, type drift 62/62), so PRs report it without failing and only the nightly run files issues; quality rules and freshness are declared but enforced downstream (dbt/GE), not by this checker; regenerating contracts needs `--force` and a version bump.

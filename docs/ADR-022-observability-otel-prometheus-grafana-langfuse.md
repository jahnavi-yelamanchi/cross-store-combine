# ADR-022: OpenTelemetry traces, Prometheus metrics, Grafana as code, Langfuse for LLM calls

- Context: a reconciliation run crosses CDC, detection, proposals, the LLM tiebreak and ledger apply; we need per-run traces, fleet metrics (bad writes, $ per 1k entities, CDC lag, latency) and per-call LLM records without tying the code to one vendor.
- Decision: `xstore.observability` wraps an OpenTelemetry TracerProvider (spans `pipeline.run` > step spans > `agent.tiebreak` / `ledger.apply_pending`, `xstore.run_id` on every span) with the exporter picked from env (OTLP/HTTP if `OTEL_EXPORTER_OTLP_ENDPOINT` and the exporter package exist, console on `XSTORE_OTEL_CONSOLE=1`, else none); prometheus_client metrics in a dedicated registry; Grafana dashboard, provisioning and Prometheus alert rules committed under `observability/`; tiebreak generations sent to Langfuse only when its credentials are set.
- Alternative rejected: a vendor APM SDK (Datadog/New Relic) for traces and metrics, and logging LLM calls to our own table.
- Why: OTLP and the Prometheus exposition format are accepted by every major backend, so the collector or SaaS can change without code edits; Langfuse adds prompt/usage/cost views per generation that generic tracing lacks; dashboards as JSON are reviewed like code.
- Consequence: local runs and tests open no ports and send nothing (in-memory exporter, `render()` instead of a server); metrics live in a process-global registry so counters accumulate across runs in one process; the OTLP exporter is not a dependency and must be installed where traces are shipped; Langfuse receives request refs and decisions, never store evidence.
